# RiverGuard — 房主权威德州扑克锦标赛（纯前端）

德州扑克锦标赛网页游戏。没有 Firebase、没有 Node 后端、没有数据库：牌局引擎跑在房主浏览器里，玩家之间通过公共 MQTT WebSocket 中继同步数据。放到任意静态托管（Gitee Pages / GitHub Pages / Vercel / Netlify / 对象存储）即可运行。

## 架构

```
房主浏览器（权威）                        玩家浏览器（哑客户端）
├── 洗牌 / 发牌 / 牌堆                     ├── 只保存自己的底牌
├── 下注合法性校验                         ├── 提交动作意图（Check/Call/Raise/Fold/All-in）
├── 主池 / 边池 / 摊牌比牌 / 淘汰排名       ├── 渲染公开状态
├── 盲注定时器（本地时钟）                  └── 心跳监控房主是否在线
└── 广播公开状态 + 定向加密发送底牌
                     │
                     ▼
        wss://broker-cn.emqx.io:8084/mqtt   （备用：broker.emqx.io、broker.hivemq.com）
```

- 房主 = 逻辑服务器：完整牌堆与全部底牌只存在于房主内存，牌堆从不广播。
- 玩家 = 哑客户端：只发动作指令，所有合法性判定都由房主执行。
- 掉线：房主心跳中断 12 秒后，所有玩家看到“房主离线”提示；房主刷新页面后可点“恢复上次房间”从本地存档继续。

## 运行与部署

本地预览必须走 http/https：**双击 `index.html`（`file://`）不行**，浏览器会拦截 ES Module，`crypto.subtle` 也不可用，页面只会一直停在初始化的转圈上。

用内置的零依赖服务器（只依赖 Node，不需要 npm 安装任何东西）：

```powershell
node tools/serve.mjs
```

然后访问 `http://localhost:8080`。想换端口就加参数，例如 `node tools/serve.mjs 9000`。

如果你有 npm，也可以 `npx --yes serve .`，或用 VS Code 的 Live Server 插件。页面在 `file://` 下打开或脚本加载失败时，5 秒后会自动显示原因和解决办法，不会再无限转圈。

### 一台机器上多开测试

同一浏览器的每个标签页/窗口都会拿到独立的玩家身份（身份存在 `sessionStorage`，并在 `localStorage` 里用标签页心跳互斥），所以可以直接开两个窗口，一个当房主、一个当玩家，也可以再开第三个窗口当第二名玩家。复制标签页时会自动分配新身份，不会和房主撞号。

两点注意：

- 房主存档存在当前标签页的 `sessionStorage` 里，所以“恢复上次房间”只在**同一个标签页刷新后**出现；关掉标签页就丢失存档。
- 房主与玩家必须连在同一个中继节点上。握手时会自动对齐节点：如果发现房主在另一个节点，会切换到房主所在的节点重新握手。

部署到 Gitee Pages 时，把仓库根目录（`index.html` 与 `js/`）作为发布目录，无需构建步骤；GitHub Pages、Vercel、Netlify 同理。

`mqtt.js` 从 CDN 引入，代码按 unpkg → jsDelivr → fastly 的顺序自动回退。若托管环境无法访问这些 CDN，可自行下载 `mqtt.min.js` 放到 `vendor/` 并调整 `js/net.js` 里的 `SDK_CDNS`。

## 通信协议

| 主题 | 方向 | 用途 |
| --- | --- | --- |
| `riverguard/v1/{房间码}/c` | 双向 | 入房握手、动作提交、玩家心跳 |
| `riverguard/v1/{房间码}/h/{房主密钥}` | 房主到全体 | 公开状态、私有底牌、种子请求、心跳、最终公示 |

消息类型：`HELLO`、`HELLO_ACK`、`JOIN_ROOM`、`JOIN_ACK`、`JOIN_DENIED`、`STATE_UPDATE`、`PRIVATE_CARDS`、`SEED_REQUEST`、`SEED_REVEAL`、`HAND_REVEAL`、`PLAYER_ACTION`、`PING`、`HEARTBEAT`、`RESYNC`。

三层保护：

1. 房间密钥层：所有报文用房间码经 PBKDF2（15 万次迭代）派生的 AES-256-GCM 密钥加密，扫频道的路人看不到牌局内容。
2. ECDH 定向层：每位玩家加入时生成 P-256 密钥对，房主与其协商共享密钥，底牌在此基础上再加密一次。其他玩家即使监听同一频道也无法解密你的底牌。
3. 身份令牌层：房主通过 ECDH 加密通道下发一次性令牌，之后的动作指令必须携带令牌，防止其他房间成员冒名操作。

## 界面说明

首页只有标题、创建房间和加入房间两个入口。游戏内没有桌面图形，只有围绕中央环形排布的座位：每个座位左侧竖排显示头像、昵称和筹码量，右侧显示这个人的底牌；自己的底牌就长在自己的座位里。牌面采用经典牌型布局，数字加粗放大后放在左上角，花色只露出左上 3/4（右下角被裁切）。公共牌在中间逐张翻开，底池用一条下划线标在中央，房间号与盲注/升盲倒计时都在顶部栏（左上房间号、右上盲注）。座位按椭圆弧长均匀分布，尺寸随容器与人数自动缩放，2 到 9 人都不会互相重叠，也不会压到底池或下方的行动栏。下注筹码显示在座位与中央之间的连线上，始终位于座位方框之外，也只显示金额，不再出现「跟注 50」这类文字；因为一轮下注结束后引擎会先停一拍再发下一条街，所以最后一次跟注的筹码量一定能看清。全下时不再一次性发完公共牌，而是按翻牌、转牌、河牌一条街一条街发出；全下的座位显示红色呼吸灯，行动权所在的座位高亮，轮到和交棒时光晕都会平滑淡入淡出。摊牌时只翻开对手的底牌，自己的牌不动。行动栏会一直显示，不在自己回合时禁用；除数字输入框外的按钮等宽，跟注文字换行时整条自动加高。

结算到下一手之间有一整套过渡动画，而且顺序是分开的：一轮下注结束、下注筹码滑向底池后淡出；一手结束进入下一手时，旧的公共牌向上淡出、底池淡出、所有下注额清空，**等这段复位演完才发新手牌**，不会出现"旧牌退场和新牌发牌挤在同一帧"的混乱。每次退场动画只播放一次，状态重播不会让它重播。摊牌时公共牌会闪一下金光，庄家以外公开的底牌带金色描边并翻牌进入，赢家座位高亮脉冲，其筹码量位置先被「+赢取额」取代（绿色弹出），1.6 秒后淡回结算后的新筹码量；即使这一手有人被淘汰，被淘汰的座位也会保持常亮，等下一手开始才变暗，保证摊牌动画看得见。右侧只有「牌局动态」，会记录每一手开始的盲注、每次下注、以及翻牌/转牌/河牌发出的具体牌面与摊牌结果；最终排名只在锦标赛结束时出现，同时房主会看到「再开一局」按钮，房主和玩家都能「返回主界面」。座位与牌面都没有描边，改用渐变和投影做层次。

动画包括：发牌（底牌从桌心飞向座位）、下注（筹码飞向下注额）、弃牌（手牌飞走并变暗）、公共牌翻牌、摊牌结算（赢家发光并浮出获得的筹码）。

`tools/preview.html` 是一个开发夹具：它复用 `index.html` 的样式渲染一手假牌局，并用无头浏览器读取座位坐标、字体和背景色，用来回归检查布局问题。

## 公平性：可验证洗牌

房主既是裁判又是玩家，所以用承诺-揭示机制限制房主：

1. 开房瞬间生成 32 字节房主密钥，立刻公开 `SHA-256(房主密钥)` 作为承诺，此时还没有任何玩家种子。
2. 每手牌开始前，房主向所有玩家索取随机种子，玩家各自生成并提交。
3. 牌堆由 `HMAC-SHA256(房主密钥, 手号 + 排序后的玩家种子 + 计数器)` 驱动的 Fisher-Yates 洗牌决定，过程完全确定，房主没有中间选择空间。
4. 发牌后 `SHA-256(牌堆)` 随公开状态广播并留档。
5. 锦标赛结束时房主公开原始房主密钥，任何玩家都能在页面上复算整场：校验密钥与开房承诺一致、复算每一手牌堆、核对底牌与公共牌是否真的来自承诺牌堆。

由于房主密钥在玩家种子出现之前就已承诺且不可更改，房主无法“看到种子后再挑一副对自己有利的牌堆”。校验在后台自动完成，只有在发现问题时才会弹出提示。

## 安全边界（请务必阅读）

这套方案适合熟人娱乐局，它不是免信任系统：

- 房主能看到全部底牌。房主浏览器就是服务器，这是房主权威架构的固有代价。可验证洗牌限制了房主换牌堆，但挡不住房主直接偷看，也挡不住房主在别人思考时用脚本外挂。
- 公共 Broker 没有认证。任何人只要知道房间码就能订阅该房间的公开状态，请把 6 位房间码当作口令。需要更私密时可自建带账号的 Broker 并替换 `js/protocol.js` 中的 `BROKERS`。
- 房间码是弱密钥。PBKDF2 迭代只能提高暴力破解成本，无法让 6 位房间码变成强密码；知道房间码的人能解开加密报文。
- 中继可用性不受我们控制。公共 Broker 可能限流、重启或断线，已配置多节点回退与自动重连，动作消息还做了应用层去重与状态定期重播，但关键时刻仍可能丢消息。
- 不要用于真钱赌博。本代码仅用于技术演示与娱乐。

如果需要“任何一方都无法单独作弊”，需要另一种架构（服务端权威、mental poker 或阈值加密），这已超出纯前端加公共中继的能力范围。

## 与旧版 Firebase 方案的差异

`legacy-firebase/` 保留了原先的 Cloud Functions + Firestore 实现作为对照：

| | Firebase 方案 | 当前方案 |
| --- | --- | --- |
| 权威方 | 云函数（房主也无法作弊） | 房主浏览器（房主可见全部底牌） |
| 部署 | 需要 Blaze 计费与 Cloud Scheduler | 纯静态托管，零后端成本 |
| 底牌隔离 | Firestore 安全规则 | ECDH + AES-GCM 定向加密 |
| 公平性 | 服务端洗牌 | 承诺-揭示可验证洗牌 |
| 国内可达性 | 依赖 Firebase 域名 | 公共 MQTT WebSocket，可自建中继 |
